## The improvement plan (next session)

1. **Two candidates per band, fallback on failure.** `morning._discover` returns a ranked list (up to `MORNING_CANDIDATES` 2):
   (a) a **good** known pair - `brain.pair_quality` of the (cell, anchor) pair, same-site preferred, with a loss/jitter cap
   (`MORNING_PAIR_MAX_LOSS` ~2 %, `MORNING_PAIR_MAX_JITTER` ~20 ms); then (b) RSRP. The run tries `#1` (serving) then the
   candidates in order; the band's A/B uses the **first leg that measures** (ok + 5G gate); a failed candidate is recorded and
   skipped; the extra cost is only paid when a candidate fails (today: 2 failed #2 legs).
2. **Do not prefer a bad known pair.** Replace `_known_pair`'s boolean priority with the pair-quality rank; a known pair with
   loss/jitter over the caps ranks as an unknown cell (behind a stronger RSRP neighbour).
3. **Dead-cell cache** (morning): a cell with `MORNING_DEAD_N` (2) consecutive no-internet/not-reachable legs in the last
   `MORNING_DEAD_DAYS` (7) is tried last / skipped; the night screen already has `_dead_cells`.
4. **Short failure path:** a candidate with no online link after `MORNING_DEAD_S` (90) or no 5G after `FIVE_G_WAIT_S` fails
   fast, so the fallback starts after ~2 min instead of ~5.
5. **Tests first (red):** a scenario with the real 202 data (a known-poor pair vs a stronger unknown; the #2 fails, the #3
   measures; the A/B uses the measured one; the dead cache; the short path). Then re-run the morning (the next 08:00 or
   manually) and validate. **Separately** run the first v lock test (manual single cell or the next night/Sat) and check
   `load_s` / the loaded quality / the score.
